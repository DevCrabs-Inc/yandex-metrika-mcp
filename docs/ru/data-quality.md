# Корректность данных

HTTP-ответ 200 сам по себе не значит, что данные корректны. Сервер соблюдает правила ниже, а нарушения возвращает как явные ошибки или предупреждения.

## Периоды и часовой пояс

- Границы считаются в часовом поясе счётчика из его настроек, а не в часовом поясе компьютера и не всегда по Москве. Если часовой пояс неизвестен, отчёт не строится (`TIMEZONE_UNKNOWN`).
- Даты включительные. Високосные годы и границы месяцев учитываются.
- Завершённый день ещё не значит «окончательно обработанные данные». Если API сообщает задержку обработки, появляется предупреждение `DATA_LAG`.

## Семплирование

- `accuracy: "strict"` (по умолчанию) запрашивает полные данные. Ответ принимается, только если API явно сообщил `sampled=false` и признаки выборки не противоречат друг другу. Иначе возвращается `QUALITY_REQUIREMENT_NOT_MET`.
- `accuracy: "balanced"` принимает выборку. В ответе указывается её доля и добавляется предупреждение `SAMPLED_DATA`.
- Если признак не пришёл, он считается неизвестным, а не означает «без выборки». Автоматического перехода из strict в balanced нет.

## Итоги и неаддитивные метрики

- Итоги (`totals`) берутся из API, а не складываются из показанных строк.
- Посетителей (`users`) нельзя складывать по дням, источникам и страницам: один человек попадает в несколько строк. Проценты и средние не усредняются по строкам.
- Достижения цели (`reaches`) — это срабатывания, а не заявки и не уникальные клиенты. Целевые визиты (`visits`) — визиты хотя бы с одним достижением.

## Сравнения

- `delta_abs` = текущее − базовое.
- `delta_pct` = изменение в процентах от базового. При нулевой базе процент не определён, поле `reason` равно `zero_baseline`.
- Для процентных метрик `delta_pp` показывает изменение в процентных пунктах: 2% → 3% это +1 п.п. и +50%.
- Сегменты сравниваются по 100 крупнейшим строкам каждого периода. Если сегмент есть только в одном периоде и строки неполные, значение «неизвестно», а не 0.
- При разной длине периодов, их пересечении или разной доле выборки появляются предупреждения.

## Временные ряды

- API возвращает значения без подписей интервалов, поэтому ось строится по календарю. Длина ответа обязана совпасть с числом интервалов, иначе возвращается ошибка `UPSTREAM_SCHEMA_CHANGED`.
- Недельный ряд должен начинаться с понедельника: тогда границы недель однозначны.
- Интервал, обрезанный периодом, помечается `partial`, а интервал с сегодняшним днём — `complete: false`.
- Итог за период считается суммой интервалов только для аддитивных метрик. Для посетителей, долей и средних он равен `null`.

## Неизвестное не равно нулю

Различаются числовой 0, «неизвестно» (`null`), пустая выборка, скрытые по приватности значения (`PRIVACY_SUPPRESSION`) и отказ в доступе. Строки с пустым названием не удаляются.

## Подписи

URL, UTM-метки и названия страниц — внешние данные. По умолчанию из URL удаляются query-строка и фрагмент (`LABELS_REDACTED`), а идентичность строки сохраняется отдельным ключом. Длинные подписи обрезаются.

## Сверка с интерфейсом Метрики

Расхождение с интерфейсом само по себе не доказывает ошибку. Сначала сравните период, часовой пояс, сегменты и фильтры, модель атрибуции, цели, семплирование и время получения. Сервер не добавляет фильтр роботов и не меняет атрибуцию незаметно: все условия видны в поле `query` ответа.

## Кэш

| Данные                    | Время жизни |
| ------------------------- | ----------- |
| Настройки счётчика и цели | 10 минут    |
| Отчёты за завершённые дни | 15 минут    |
| Отчёты, где есть сегодня  | 60 секунд   |

`cache: "refresh"` обходит кэш. `cache: "allow_stale"` при недоступности API отдаёт старые данные с предупреждением `STALE_DATA` и исходным временем получения. Кэш хранится только в памяти процесса.
