# Requirements

This is the public summary of the product requirements for yandex-metrika-mcp. Code comments, test names and docs cite requirement IDs such as `D-01` or `T06`; this file defines them.

The requirements describe intended behaviour. What is already verified, and with which evidence, is tracked in [release-checklist.md](release-checklist.md). Facts about the Yandex API and their verification status live in [api-notes.md](api-notes.md). Layering and code rules are in [AGENTS.md](../AGENTS.md).

## ID families

| Prefix                                                       | Meaning                                                                      |
| ------------------------------------------------------------ | ---------------------------------------------------------------------------- |
| `UX`, `ACC`, `REP`, `EXP`, `API`, `SEC`, `OPS`, `OSS`, `DOC` | Functional and non-functional requirements                                   |
| `D-xx`                                                       | Data-correctness rules                                                       |
| `Txx`                                                        | Required test scenarios                                                      |
| `Gx`                                                         | Release gates                                                                |
| `Exx`                                                        | Known failure modes that the design must prevent                             |
| `P0`, `P1`, `P2`                                             | Priorities: P0 is required for v1.0, P1 is a later phase, P2 is out of scope |

Numeric limits such as quotas, TTLs and storage budgets are product settings unless they are marked as Yandex limits. The current values are in [docs/ru/configuration.md](ru/configuration.md).

## Scope

v1.0 is a local stdio server that reads aggregated data from the Reporting API and read-only Management endpoints (counters, settings, goals). Remote mode (gate G4) and the Logs API (gate G5) are later phases and are not part of v1.0.

Other later-phase (P1) IDs: `REMOTE-01` (authenticated self-hosted Streamable HTTP), `LOG-01` (opt-in Logs API profile), `ANA-01` (a change-analysis tool), `INT-01` (native MCP Tasks for clients that support them, with job tools and text kept as the baseline) and `OPS-02` (a separate worker process for long jobs). Tests T35-T41 belong to these phases.

Out of scope (P2): writes to the Management API (goals, counters, access, expense or offline-conversion imports), arbitrary SQL, file system access through model arguments, arbitrary HTTP requests, a built-in LLM, and scheduled tasks or notifications.

## Data-correctness rules

A report is not correct just because the API returned HTTP 200. User-facing explanations of these rules are in [docs/ru/data-quality.md](ru/data-quality.md).

| ID   | Rule                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          |
| ---- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D-01 | Sampling and accuracy. Read the real `sampled`, `sample_share`, `sample_size` and `sample_space` fields; a missing `sampled` is unknown (null), never false. Strict mode (the default) requests `accuracy=full` and accepts a result as unsampled only on an explicit `sampled: false` with no contradicting fields, otherwise it returns `QUALITY_REQUIREMENT_NOT_MET`; balanced mode allows sampling with a warning, and the server never lowers accuracy on its own.                                                                                                                                                       |
| D-02 | Periods, time and freshness. The timezone comes from the counter settings, not the machine or a fixed zone, and an unknown timezone is never guessed; dates are validated against the calendar, day ranges are inclusive, and the defaults are the last 7 complete days for a report and the last two complete ISO weeks for a weekly comparison. The current day is allowed only with `period_complete=false`, freshness (`fetched_at`, data lag, cache age) is reported separately from period completeness, unequal periods get a warning, and hourly grouping stays off until its behaviour across DST changes is tested. |
| D-03 | Reproducibility. Provenance records what is needed to repeat the query (counter, connection, dates, timezone, metric, dimension and goal IDs, filters, attribution, unit, requested and observed accuracy, preset, catalog and adapter versions, source method, `fetched_at`) plus a deterministic query fingerprint without secrets. The server never silently adds a robot filter or changes attribution, goals, grouping or currency to make a query succeed; applied transformations appear in the applied query and in warnings, and suggested corrections are never applied automatically.                              |
| D-04 | Totals, units and non-additive metrics. Use API totals; rows may be summed only for a complete, disjoint grouping of an additive metric, so unique users are never summed and rates or averages are never averaged with a plain mean. Units are explicit, goal reaches are not goal visits or leads, missing ecommerce setup is not zero revenue, large numbers keep full precision, and missing or unsuitable totals are unknown.                                                                                                                                                                                            |
| D-05 | Missing data and privacy suppression. Zero, null or unknown, an empty selection, an unconfigured feature, missing permission, an API refusal and incomplete output are distinct states that are never converted into each other; suppressed values are not guessed or set to zero, and a row with an empty label keeps a stable key. Unrecognised critical schema fields raise `UPSTREAM_SCHEMA_CHANGED`, while extra optional fields are tolerated.                                                                                                                                                                          |
| D-06 | Pagination and completeness. The Reports API offset is 1-based, its maximum `limit` is not a default page size, and `total_rows_rounded` means the row count is approximate. Exports use a fixed normalized query and stable sort, bounded pages and budgets, per-page checks and checksummed checkpoints, and end as complete, partial or unknown with a reason. A repeated page or drift leads to one bounded restart or a partial result, never silent deduplication, and an early empty page, timeout, disk limit, sampling change or schema drift is not a successful end.                                               |
| D-07 | Comparisons. `delta_abs = B - A` and `delta_pct = (B - A) / A * 100` when A is not zero (otherwise null with reason `zero_baseline`); rate metrics also get `delta_pp` in percentage points, and unknown inputs give unknown, never 0 or Infinity. Comparisons use the union of keys from both periods, a row missing from a top-N list is unknown unless zero is confirmed, and a difference between segments is an observation, not a causal claim.                                                                                                                                                                         |
| D-08 | Time series. Use the upstream time axis when there is one; rebuilding it is allowed only for tested combinations of dates, timezone and grouping, and the number of values must match the number of buckets. Months are calendar months, incomplete first and last buckets are marked, gaps are not interpolated, and `top_keys` limits the number of series, so the overall total is not the sum of the shown series.                                                                                                                                                                                                        |
| D-09 | Evidence and labels. URLs, page titles, search phrases, UTM tags and goal names are external data that may contain personal data or instructions; they are passed as data and never trigger actions. Safe mode removes query strings and fragments from displayed URLs while keeping an opaque row key (this is not full anonymisation), only a user policy set outside tool arguments can widen privacy, and redacting labels never changes numeric totals. In P1 analysis, every computed observation carries evidence and separates facts, hypotheses and suggested checks.                                                |
| D-10 | Logs API (P1). Raw logs are an opt-in profile with its own storage policy and an evaluate, create, poll, download, validate, publish and clean lifecycle. A create request is never repeated blindly after a timeout, cleanup removes only requests this system created, and "all fields" is never the default.                                                                                                                                                                                                                                                                                                               |

In code, keep `null` for unknown values, use API totals, and pass labels from the API through `safeLabel`. Add a regression test for every new data-correctness rule.

In live reconciliation with the Metrika UI, unsampled integer counts must match exactly when the data has not changed, and rates and averages are compared with a numerically justified epsilon rather than a blanket percentage tolerance. ## Known failure modes

These IDs name mistakes that a Metrika MCP server can make, and the requirement that prevents each one.

| ID  | Failure mode                                                                                                       | Prevented by                                                               |
| --- | ------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------- |
| E01 | Reading sampling from the wrong response field, so sampled data looks exact.                                       | D-01, T01-T03                                                              |
| E02 | Read-only tools next to a generic request tool that can write, guarded only by a confirmation flag the model sets. | SEC-01: no write route is registered; a route allowlist and negative tests |
| E03 | An HTTP transport without built-in user authentication presented as a ready remote service.                        | REMOTE-01, T35-T37                                                         |
| E04 | Sending `Authorization: Bearer` while Yandex documents `Authorization: OAuth`.                                     | API-01: contract fixture and a live smoke check                            |
| E05 | "Today" or a fixed Moscow timezone as the universal default for comparisons.                                       | D-02, T04, T05, T10                                                        |
| E06 | A default filter that changes the numbers without being visible.                                                   | D-03: applied query and UI parity fixtures                                 |
| E07 | A large API surface and a hard first run.                                                                          | UX-01...UX-04                                                              |

## MCP contract principles

User-facing tool descriptions are in [docs/ru/tools.md](ru/tools.md), exports in [docs/ru/exports.md](ru/exports.md), error codes in [docs/ru/troubleshooting.md](ru/troubleshooting.md) and [src/domain/errors.ts](../src/domain/errors.ts).

- **Transport.** v1.0 speaks MCP over stdio (protocol revision 2026-07-28). stdout carries only protocol messages; logs go to stderr with redaction.
- **Fixed, read-only tool set.** The 13 P0 tools are `metrika_status`, `metrika_connect`, `metrika_disconnect`, `metrika_list_counters`, `metrika_describe_counter`, `metrika_catalog`, `metrika_run_report`, `metrika_compare_periods`, `metrika_run_timeseries`, `metrika_export_report`, `metrika_get_job`, `metrika_cancel_job` and `metrika_read_artifact`. The set is fixed by the configuration profile at startup and never changes as a side effect of a call. Access is still checked on every call.
- **Annotations.** Reads get `readOnlyHint: true`, and `openWorldHint` reflects calls to the external API. Connect, disconnect, export and cancel have side effects and are not marked read-only. Annotations help clients but do not replace scopes, the route allowlist or server-side checks.
- **Explicit context.** Every analytics call takes `connection_id` and `counter_id`. The server never falls back to the last used connection or counter. An alias is for display only; the ID is the key.
- **Result shape.** Results carry `schema_version`, `kind`, `status` (`success` or `empty`; comparisons can also be `partial`; errors are `error`), `request_id`, the resolved query, data with upstream totals, independent quality flags, provenance, warnings and `next_cursor`. Values are not mixed with formatted strings.
- **Errors.** Domain and API failures are `tools/call` results with `isError: true` and an `error` object: `code`, a safe `message`, `retryable`, `retry_at`, `next_action` and optional `details` (`field`, up to 5 `candidates` as `{id, label}`, `upstream_message`). A valid partial or empty result has `isError: false` and reports its quality. JSON-RPC errors are only for protocol violations. Errors never contain request headers, raw upstream bodies or tokens. Text from Yandex goes only into `details.upstream_message`. Candidates come only from the catalog and from resources of the same connection, are never applied automatically (D-03), and are not given for `ACCESS_DENIED`, `JOB_NOT_FOUND` or `ARTIFACT_NOT_FOUND` (T21).
- **Response budget.** Inline JSON plus summary text stay within 48 KiB UTF-8 in total; tables default to 20 rows, at most 200. Serialized JSON is never cut at a character count, quality and provenance are always kept, and a shortened result states the reason in `quality.truncation_reason` (`page_limit`, `byte_budget` or `top_n`). Large JSON is not duplicated in both the text content and `structuredContent`.
- **Cursors.** `next_cursor` is signed and tamper-proof, bound to the connection, the query fingerprint, the sort order and an expiry. A cursor from another query or connection is rejected (`CURSOR_MISMATCH`); an expired one means repeating the report (`CURSOR_EXPIRED`).
- **Jobs and artifacts.** Creating an export requires an `idempotency_key`: the same key and query return the same job, and a different query gives `IDEMPOTENCY_CONFLICT`. Job states are `queued`, `running`, `completed`, `waiting_quota`, `interrupted`, `partial`, `failed` and `cancelled`; `partial` is never reported as `completed`. Artifacts have random IDs, and reading one repeats the tool's authorization. The model never passes a file path or URL.

## Data-correctness principles

The full rules are in the table above and in [docs/ru/data-quality.md](ru/data-quality.md). In short:

- Unknown is not zero: keep `null` for unknown values, sampling and missing segments.
- Use API totals. Never sum non-additive metrics or average rates across rows.
- Periods are complete and use the counter timezone by default; an unknown timezone is an error, not a guess.
- Strict accuracy is the default and never falls back to balanced on its own.
- Never change filters, attribution, goals or grouping silently; report what was applied.
- Labels from the API are untrusted data and are sanitized before they reach the model.

## Security principles

Details are in [SECURITY.md](../SECURITY.md) and [docs/ru/privacy-security.md](ru/privacy-security.md).

- **No secrets in tool I/O.** No tool accepts a token or an authorization code, and secrets never appear in tool results, logs, errors or diagnostics. MCP elicitation is not used to collect secrets.
- **Public PKCE client.** Sign-in uses Authorization Code with PKCE (S256) and `state`. No client secret is shipped in the package. Refresh is used only where it works for this client type; otherwise signing in again is the normal path.
- **Local loopback sign-in page.** It listens only on the loopback interface, checks `Host` and `Origin`, uses a random one-time link with a short TTL, loads no external resources and removes the code from the URL after the callback. The link never contains tokens, a client secret or the PKCE verifier.
- **Credential storage.** Tokens live in the OS credential store. There is no silent plaintext fallback; an unencrypted file store is an explicit opt-in.
- **Read-only routes.** The API adapter uses HTTPS and a fixed allowlist of official hosts and paths. Tool arguments never control the host, headers, proxy, file paths or commands. There is no Management API write, raw HTTP tool or `request(path)` escape hatch.
- **Isolation.** Cache, jobs, artifacts and cursors are bound to a connection and its generation. Resources of another connection look the same as missing ones.
- **Telemetry off.** Nothing is sent outside by default. If an opt-in is ever added, it must not collect analytics data. Diagnostics from `doctor` contain no tokens, URL query strings or analytics values; the user reviews them before sharing, and the server never sends them itself.
